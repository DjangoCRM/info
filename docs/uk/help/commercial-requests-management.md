# **Управління комерційними запитами**

Комерційні запити в [Django CRM](../index.md) допомагають командами продажів відстежувати потенційних клієнтів, які шукають конкретні продукти або послуги. Запит часто є першим кроком до створення угоди та запуску процесу продажів.

Ця сторінка пояснює, як користувачі CRM керують комерційними запитами, які права доступу застосовуються, та як ефективно працювати зі списком запитів.

## **Що таке комерційні запити?**

Запит містить [основну інформацію](request-processing.md) про запит клієнта: що саме він хоче придбати, від кого представляється та його контактні дані. Ці записи можуть з’являтися в CRM кількома способами:

- **Автоматично** з веб-форми
- **Автоматично** з вибраних вхідних електронних листів (якщо налаштовано)
- **Вручну** додані користувачем CRM
- **Скопійовані** з існуючого запиту (щоб заощадити час на повторювані звернення)

Підтримувати запити повними та точними важливо — правильні контактні дані дозволяють CRM зіставляти компанії, ліди та контакти, які вже є в базі даних.

---

## **Ролі користувачів, які працюють із запитами**

Існує **три ролі**, безпосередньо пов’язані з обробкою запитів:

| Роль | Обов’язки | Рівень доступу |
| ---- | -------- | -------------- |
| **Оператор** | Обробляє запити, створює угоди, призначає менеджера з продажів | Лише у межах призначеного відділу |
| **Супер-оператор** | Керує запитами для всіх відділів | Усі запити компанії |
| **Менеджер з продажів** | Створює запити та угоди | Лише у межах призначеного відділу |

Якщо CRM використовується в малому бізнесі, одна й та сама особа може виконувати ролі оператора **та** менеджера з продажів.

Менеджери з продажів переважно працюють з **угодами**, а не із запитами. Оператори переводять кваліфіковані запити в угоди та призначають їх для подальшої роботи. У випадках, коли запити надходять безпосередньо менеджерам з продажів, вони самі створюють ці запити.

Щоб змінити роль або запросити додатковий доступ, зверніться до свого **адміністратора CRM**.

---

## **Коли слід створювати угоду?**

Угода представляє собою **активний процес продажів**, а не закритий контракт. Для більшості дійсних запитів угоду **потрібно створити**.

Угоду **не створюють** лише тоді, коли запит позначено як:

* **Дублікат**
* **Справа/інцидент** (запит на підтримку без комерційного потенціалу)
* **Нерелевантний** (це поле за замовчуванням приховане)

## **Як додавати запити**

Користувачі з відповідними правами можуть додавати запити:

| Метод | Як це працює |
| ----- | ------------ |
| Кнопка **Додати запит** | Відкриває порожню форму — заповніть усі обов’язкові дані |
| **Імпорт запиту з електронної пошти** | Створює запит на основі вхідного листа (спочатку потрібно налаштувати обліковий запис електронної пошти в CRM) |
| Кнопка **Копіювати** | Створює дублікат чернетки з редагованими даними |

Запити з веб-форм контакту з’являються в системі автоматично.

---

## **Керування списком запитів**

Усі запити відображаються в таблиці, яку можна сортувати. Заголовки стовпців включають:

- **Назва запиту**
- **Мітка лояльності**
  • *Основна*: згенерована маркетингом  
  • *Подальша*: прямий контакт із відомим лідами або компанією
- **Назва контрагента** (ліда або компанії)
- **Країна**
- **Контактна особа**
- **Дата запиту**
- **Призначений оператор або менеджер з продажів**
- **Статус запиту** — *в очікуванні* або *оброблено*

### **Пошук і фільтрація**

Ви можете швидко знаходити потрібні запити за допомогою:

✅ **Рядок пошуку** — пошук за ID *(id123)* або ключовими словами  
✅ **Панель фільтрів** — фільтрація за:

- Відділом (якщо дозволено роллю)
- Статусом запиту
- Призначеним оператором або менеджером з продажів
- Датою отримання
- Товаром або послугою
- Лояльністю
- Країною

## **Короткий огляд правил доступу**

| Тип користувача | Що він може переглядати |
| --------------- | ----------------------- |
| Оператор | Запити свого відділу |
| Менеджер з продажів | Запити свого відділу (призначені йому) |
| Супер-оператор | Запити всіх відділів |
| Менеджер компанії | Повна видимість у всьому CRM |
